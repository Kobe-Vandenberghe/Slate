# 2026-09-30 — ArchDoc v1: canonical board model

## Goal
Define Slate's canonical, JSON-based model language (ArchDoc v1) and plan its staged implementation.
It must be the source of truth for the board, carry optional architecture meaning, round-trip losslessly
with the canvas, be sliceable for AI, and act as the interchange layer for Mermaid, files, etc.

## Decisions
See `docs/archdoc.md`. Key points:
- Separate connections list, not nested under elements; the AI projection nests them under the source.
- Use `kind`, not `type`.
- No `null` property values.
- Waypoints are in board coordinates.
- Array order = sibling z-order, with no global frame-first rule.
- Strict JSON, no comments.
- Frames have no nesting or rotation, and their children use relative coordinates.
- Aliases are slugs, and ids are opaque.

## Roadblocks & edge cases
- In the current code `kind` means geometry. It must be renamed everywhere to `shape` in stage 2a, never half-done.
- Sticky and shape palettes share names with different colors, so token resolution depends on `shape`.
- Connectors are currently interleaved in z-order with shapes; after stage 2b they always draw on top.
- Existing boards may contain hex colors not in the palette. The migration needs a fallback token.
- Stage 1: rounding anchors to 2 decimals would move an end by up to 4px on an 800px frame, so anchors use 4.
- Stage 1: an empty `alias` failed the slug check. Empty alias/kind/label are now treated as absent.
- Stage 1: reference checks on a doc that already has field errors produced cascading duplicate errors, so
  they only run once the fields are valid.
- Stage 2a: the type is `ShapeType` rather than `ShapeKind`, and parameters of that type are named `type`, since
  `shape` is already the variable name for `Shape` objects.
- Stage 2a: v3 always paired fill + stroke from one palette entry, so the migration keeps only the fill token
  (connectors: the stroke token). A sticky recolored from the shape palette (e.g. shape-yellow `#fff3a3`) now
  shows sticky-yellow. The shift is minor and accepted.
- Stage 2a: radians → degrees gave float noise (29.999999999999996), so the migration rounds to 1e-6.
- Stage 2a: the app only saves on change, so a freshly migrated board stays in v3 form in localStorage until the
  first edit. That is harmless because it re-migrates on every load.
- Stage 2b-1: split 2b so the stored format lands first. 2b-2 changes only the in-memory model, with no migration.
- Stage 2b-1: migrations need the legacy title (a separate key), so `MIGRATIONS[n]` takes `(data, legacyTitle)`.
- Stage 2b-1: a comment between two `case` labels trips ESLint `no-fallthrough`. Put it above both.
- Stage 2b-1: an invalid stored board used to silently become `[]` and then be overwritten on the next edit. It is
  now copied to `miroclone:board:corrupt` first.
- Stage 2b-1/2: twice, a journal edit that ran in the same parallel batch as `git commit` missed the commit. Edit
  first, commit after.
- Stage 2b-2: `create_file` cannot overwrite, so full rewrites made stray `*.tmp` / `*.next.ts` files. Edit in
  place (or `git mv` first, then edit).
- Stage 2b-2: connection paths are derived on every render. A WeakMap keyed by the immutable diagram object makes
  that one computation per change, shared by the renderer, selection bounds and the toolbar.
- Stage 2b-2: deleting an element must detach its connections at their *current* resolved points, so
  `removeFromDiagram` reads `connectionPaths(d)` before removing. Copy uses the same trick (`extractSelection`).
- Stage 2b-2: smoke tests with two fast clicks at one spot trigger the custom double-click (opens the editor).
  Wait past `DOUBLE_CLICK_MS` between clicks.
- Stage 3: `Meaning` (all-optional fields) is a TS "weak type", so `{ id }` literals failed. Adding the required
  `id` fixed it, and real elements and connections always have one.
- Stage 3: browser tabs that aren't visible don't render frames, so Playwright clicks time out waiting for
  "stable". Open a fresh (visible) page.
- Stage 3: the first property layout (key | value | type | × in one row) truncated both key and value at 272px.
  Now key/type/× sit on the first line and the value spans the second.
- Stage 3: no schema change was needed. The format already had kind/alias/label/properties, so the UI only
  had to start writing them.
- Stage 4: keeping children frame-relative in memory (spec + ADR 0009) means two coordinate spaces. The fix is one
  cached world view (`worldElements`) that everything visual/geometric reads, with edits writing stored coordinates.
  Translate and resize deltas are space-independent; rotate and scale go through world space.
- Stage 4: resizing a frame from its top/left edge would drag its (relative) children along. `resizeElement` shifts
  them back.
- Stage 4: a frame body that catches clicks would block marquee and double-click-to-write inside it, so only the
  title is hit-testable, and a marquee picks a frame only when it fully encloses it.
- Stage 4: frame interiors don't catch connection ends (floating to a frame felt wrong); only the edge snaps.
- Stage 4: smoke-test pitfalls: the test window is 1067×655, so shapes went off-screen after moves and the Inspector
  covered the start point of a drag. Press Fit and deselect before each drag. Old `[vite]` console errors in "recent
  events" were HMR noise from mid-edit states, not runtime errors.

## Follow-ups
- Frames are selected by their title only. A small title at low zoom can be hard to hit.
- `zoomToContent` ignores the frame title that sits above the frame.
- ADR 0009 said stage 4 would be pure UI; in practice it needed the world view in `shapes`. The decision stands.
- Stage 5 (`.slate.json` import/export) is next.
- `ConnectionView` ignores `arrows` (always one head at `to`) and `waypoints` (straight line). Nothing creates them yet.
- Labels are edited in the Inspector only (no double-click-to-edit on the arrow yet).
- Kind/properties can't be edited for several items at once (the Inspector needs exactly one selected).
